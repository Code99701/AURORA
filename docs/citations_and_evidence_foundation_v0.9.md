# AURORA Citations and Evidence Foundation v0.9

## Implementation status

v0.9 makes RAG responses and their supporting evidence durable backend domain
objects. It extends the server-controlled source references from v0.8 without
changing the authorized retrieval or Gemini generation architecture.

The persistent provenance chain is:

```text
Workspace
  -> RAG Response
      -> ordered Citation
          -> Document Chunk
              -> Extracted Page
              -> Document
                  -> Workspace
```

Citation verification and claim-to-evidence analysis remain explicitly deferred.

## Database changes

Migration `b84cf6e207d9` creates two tables.

### `rag_responses`

Stores a stable UUID, workspace, requesting user, query, generated answer,
optional answer language, requested `top_k`, original citation count,
insufficient-evidence status, generation model, and creation timestamp.

### `rag_citations`

Stores a server-generated UUID, response UUID, actual `document_chunks` UUID,
one-based display position, retrieval similarity, and creation timestamp.

The citation does not duplicate filename, document ID, page number, or chunk
text. Those values are derived through the live chunk/document/page relationships.
Similarity and position are stored because they are facts of the retrieval event,
not properties of the reusable chunk.

Database constraints guarantee one position and one chunk per response. This
backs the application rule that repeated evidence keeps only its first occurrence
in retrieval order.

## RAG response lifecycle

```text
authenticated user
  -> authorized workspace
  -> workspace-filtered semantic retrieval
  -> relevance filtering and chunk deduplication
  -> bounded context
  -> grounded Gemini generation
  -> workspace/chunk revalidation
  -> response and citations committed atomically
  -> answer plus durable citation IDs returned
```

Generation happens before persistence. The response record and every citation
are then written in a single transaction. A persistence error rolls back all
response/citation rows and returns a safe `RAG_PERSISTENCE_ERROR`; the API does
not return an answer that falsely claims durable citations. Provider failures
create no response record.

Insufficient-evidence results are persisted with a stable response UUID and zero
citations. Gemini is still not called for that path.

## Authorization and citation identity

The client supplies only `query`, `top_k`, and optional `answer_language`.
Pydantic rejects client-supplied document, chunk, citation, or response metadata.

Citation UUIDs are generated by the server. Gemini output is never parsed for
authoritative identifiers. Before insertion, the persistence service queries all
selected chunks together with documents and requires every row to belong to the
already-authorized workspace. Returned document, filename, and page metadata is
derived from those database rows.

Response lookup requires workspace membership and applies the workspace predicate
inside the SQL query. A response UUID or citation UUID alone grants no access.
Non-member and cross-workspace access follow AURORA's concealed 404 policy.

## Deletion behavior

- Workspace deletion cascades its RAG responses, citations, documents, pages, and
  chunks.
- Response deletion would cascade its citations.
- Document, page, chunk deletion, or reindexing cascades affected citation rows.
- `rag_responses.citation_count` records the number originally associated with
  the answer. If any citation is later removed, response lookup returns concealed
  404 instead of exposing a partial or misleading provenance set.

This retains no stale filename/page snapshots and prevents deleted private source
metadata from leaking. The remaining incomplete response row can support future
internal retention policy work, but it is not API-visible.

## API contract

Generate and persist an answer:

```http
POST /api/v1/workspaces/{workspace_id}/rag
```

Retrieve a persisted response inside an authorized workspace:

```http
GET /api/v1/workspaces/{workspace_id}/rag/responses/{response_id}
```

Both return:

```json
{
  "response_id": "uuid",
  "answer": "Grounded answer",
  "sources": [
    {
      "citation_id": "uuid",
      "position": 1,
      "document_id": "uuid",
      "chunk_id": "uuid",
      "filename": "Research Paper.pdf",
      "page_number": 4,
      "similarity": 0.91
    }
  ],
  "insufficient_evidence": false,
  "model": "configured-model"
}
```

A future frontend can render citation `position=1` as:

`[1] Research Paper.pdf — Page 4`

The API never exposes storage keys, paths, prompts, credentials, chunk embeddings,
or unauthorized source metadata.

## Testing

The deterministic v0.9 suite covers response persistence, citation creation,
real chunk/page/document provenance, multi-document sources, order, duplicate
handling, workspace isolation, invalid identifiers, identifier injection,
document/workspace deletion, persistence rollback, provider failure,
insufficient evidence, and migration upgrade/downgrade/re-upgrade.

Automated tests use fake providers and consume no Gemini quota. The existing
explicit real-provider test remains opt-in and unchanged.

## Limitations and deferred work

- Citations map the answer to selected evidence, not individual answer claims.
- No second LLM or heuristic verifies that every claim is supported.
- No persistent conversation or message relationship exists yet.
- Incomplete response rows after evidence deletion are concealed rather than
  exposed or automatically purged.
- No frontend rendering, R2, reranking, hybrid retrieval, query rewriting,
  agents, LangChain, or LangGraph was added.

The next milestone is Multilingual RAG Foundation / Multilingual Evaluation.
