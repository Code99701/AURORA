# Document Management and Ingestion Foundation v0.5

Document Management v0.5 adds the secure upload and storage boundary that feeds AURORA’s later extraction and RAG pipeline. It stores validated source documents and their metadata; it does **not** extract text, create chunks, generate embeddings, or call an AI provider.

## Document entity

Each `Document` belongs to exactly one workspace and records the authenticated uploader. Its PostgreSQL metadata includes:

- UUID identifier;
- `workspace_id` and `uploaded_by` foreign keys;
- normalized original filename;
- storage provider and application-generated storage key;
- canonical MIME type and byte size;
- SHA-256 checksum;
- processing status;
- creation and update timestamps.

The API intentionally omits `storage_provider` and `storage_key` from public responses. Clients receive useful metadata without learning internal object layout.

## Why PostgreSQL stores metadata rather than binaries

PostgreSQL is responsible for relational facts: ownership, authorization scope, status, file metadata, and future relationships to extracted content and chunks. The binary is managed by `FileStorage`.

This separation keeps database backups smaller, allows file delivery to use storage-native streaming, and lets deployment move from a local disk to object storage without rewriting document business logic.

## Document lifecycle

The allowed states introduced by v0.5 are:

```text
UPLOADED -> PROCESSING -> PROCESSED
                     \-> FAILED
```

A successful v0.5 upload is always `UPLOADED`. It is not marked processed because extraction does not exist yet. v0.6 will transition documents through processing and store structured extracted content.

## FileStorage abstraction

The application uses the small provider-neutral `FileStorage` contract:

- `save(key, source)`
- `open(key)`
- `delete(key)`
- `exists(key)`

Document routes and services depend on this contract rather than filesystem APIs.

### Local MVP

Development uses `LocalFileStorage`. Its default private root is:

```text
storage/uploads/
```

The directory is ignored by Git and is not mounted as a FastAPI static directory. Files are written to a temporary sibling and atomically renamed into place. Storage keys are validated and resolved under the configured root, preventing absolute paths and `..` traversal.

### Future deployment

Deployment will use an object-storage adapter implementing the same contract. **Cloudflare R2 is the preferred deployment candidate**, but it is not required for the local MVP and no R2 credentials or SDK are part of v0.5.

## Upload flow

```text
opaque session authentication
  -> existing workspace membership authorization
  -> PDF validation
  -> generate document UUID and storage key
  -> save binary through FileStorage
  -> commit metadata to PostgreSQL
  -> return public DocumentResponse with status UPLOADED
```

The storage key is always generated by AURORA:

```text
workspaces/{workspace_id}/documents/{document_id}/original
```

The original filename is display metadata only and never controls a filesystem path.

## Validation

v0.5 intentionally supports only PDF files. An upload must pass all of these checks:

- the normalized display filename ends in `.pdf`;
- the declared MIME type is `application/pdf` or `application/x-pdf`;
- the content begins with the PDF `%PDF-` signature;
- the content is nonempty;
- the content does not exceed `DOCUMENT_MAX_SIZE_BYTES`.

The default limit is 10 MiB (`10485760` bytes) and is configurable through the environment. Validation reads the upload in bounded chunks while calculating its SHA-256 checksum. Filename path components and control characters are removed; overlong or unusable names are rejected.

These checks reduce obvious upload abuse but are not a malware scanner or full PDF parser. Structural extraction validation belongs to v0.6.

## Listing and detail

Listing queries always filter by the already-authorized workspace ID. Detail queries require both the requested document UUID and that same workspace ID, preventing a document UUID from being used across workspace boundaries.

Metadata endpoints never return the binary, storage root, storage key, provider credentials, or filesystem path.

## Download

Downloads authenticate and authorize workspace membership before querying document metadata or opening storage. The binary is streamed through `FileStorage` with a canonical PDF media type and an attachment header using the safe display filename. No storage directory is publicly exposed.

## Delete

The approved workspace permission model allows MEMBER users to upload and use documents while OWNER users manage workspace documents. Therefore deletion is OWNER-only in v0.5.

Deletion verifies the document belongs to the authorized workspace, removes the storage object, and hard-deletes its metadata. `LocalFileStorage.delete()` treats an already-missing object as a safe idempotent condition. Future milestones must remove chunks, embeddings, and citations before document deletion once those entities exist.

Deleting a workspace also removes its document storage objects before the
database cascades workspace-owned metadata, preventing orphaned local files.

## Failure handling

Upload uses a simple compensating action:

1. validate the upload;
2. save the file;
3. attempt the database commit;
4. if persistence fails, roll back and delete the new storage object;
5. return a safe error without leaking provider details.

This avoids knowingly orphaning new files without introducing distributed transactions or a queue system. Storage failures return controlled service errors. Logs do not include filenames, storage keys, credentials, or uploaded content.

## Workspace isolation and security

- Every route reuses the v0.3 session identity and v0.4 workspace dependencies.
- Missing authentication returns 401.
- Missing or non-member workspaces share the documented 404 concealment response.
- Document lookup includes both `document_id` and the authorized `workspace_id`.
- Cross-workspace listing, detail, download, and deletion are blocked.
- Storage access occurs only after authorization and document ownership filtering.
- Clients cannot supply document IDs, storage providers, storage keys, statuses, paths, or uploader IDs.
- Database constraints enforce valid status, positive size, unique storage keys, and relational ownership.
- Binaries are not stored in PostgreSQL or exposed as public static files.

## Configuration

Local defaults are shown in `.env.example`:

```dotenv
DOCUMENT_STORAGE_PROVIDER=local
DOCUMENT_STORAGE_ROOT=storage/uploads
DOCUMENT_MAX_SIZE_BYTES=10485760
```

Relative roots are resolved against the repository root, not the shell’s current directory. No cloud credentials are needed.

## Connection to v0.6

Document Processing Foundation v0.6 will start from the persisted `UPLOADED` document and its storage object:

```text
stored PDF
  -> PDF extraction
  -> text cleaning
  -> page/section metadata
  -> structured extracted content
```

Chunking, embeddings, retrieval, RAG, multilingual answers, and citations remain later stages and are not implemented in v0.5.
